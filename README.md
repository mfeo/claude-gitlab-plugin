# claude-gitlab-plugin

A **Claude Code plugin** that fetches GitLab issues and merge requests as LLM-friendly Markdown, injecting the content directly into your Claude Code conversation context.

> **Claude Code only.** This plugin uses Claude Code-specific features (dynamic shell injection, `${CLAUDE_PLUGIN_ROOT}`) that are not compatible with Codex CLI or Gemini CLI.

## Install as Claude Code Plugin

### Local / development

```bash
claude --plugin-dir /path/to/claude-gitlab-plugin
```

### Via marketplace (once published)

```text
/plugin marketplace add mfeo/claude-gitlab-plugin
/plugin install gl@mfeo-claude-gitlab-plugin
```

## Usage in Claude Code

```text
/gl:issue mygroup/myproject 42
/gl:mr mygroup/myproject 101
/gl:mr mygroup/myproject 101 --diff
/gl:mr mygroup/myproject 101 --diff --discussions
```

The fetched content is injected into the conversation. Claude can immediately summarise, analyse, or act on it.

## Environment Setup

Set `GITLAB_URL` and `GITLAB_TOKEN` in your shell or in `~/.claude/settings.json`:

**`~/.zshrc` / `~/.bashrc`:**

```bash
export GITLAB_URL="https://gitlab.example.com/api/v4"
export GITLAB_TOKEN="glpat-xxxxxxxxxxxxxxxxxxxx"
```

**`~/.claude/settings.json`:**

```json
{
  "env": {
    "GITLAB_URL": "https://gitlab.example.com/api/v4",
    "GITLAB_TOKEN": "glpat-xxxxxxxxxxxxxxxxxxxx"
  }
}
```

`GITLAB_TOKEN` requires the `read_api` scope (read-only). See [Token Scope](#token-scope) below.

## Direct CLI Usage

The scripts in `scripts/` can also be run directly without Claude Code:

```bash
./scripts/fetch-issue.sh mygroup/myproject 42
./scripts/fetch-mr.sh mygroup/myproject 101 --diff --discussions | pbcopy
```

## Token Scope

| Scope | Access | When to use |
|-------|--------|-------------|
| `api` | Full read/write API | Creating or modifying issues, MRs, notes |
| `read_api` | Read-only API (all groups, projects, registries) | **This toolkit — read-only data retrieval** |
| `read_repository` | Read-only Git repository (clone/pull) | Not needed here |

`read_api` is sufficient to call all endpoints in these scripts.

## API Endpoints

All endpoints are under `https://<gitlab-host>/api/v4`.  
`:id` accepts a numeric project ID **or** a URL-encoded path (`mygroup/myproject` → `mygroup%2Fmyproject`).

| Resource | Endpoint |
|----------|----------|
| Single issue | `GET /projects/:id/issues/:issue_iid` |
| Single merge request | `GET /projects/:id/merge_requests/:merge_request_iid` |
| Issue comments (flat) | `GET /projects/:id/issues/:issue_iid/notes` |
| MR comments (flat) | `GET /projects/:id/merge_requests/:merge_request_iid/notes` |
| Issue discussion threads | `GET /projects/:id/issues/:issue_iid/discussions` |
| MR discussion threads | `GET /projects/:id/merge_requests/:merge_request_iid/discussions` |

### Key response fields

**Issue / MR:** `title`, `description` (Markdown), `state`, `author`, `labels`, `created_at`, `updated_at`, `web_url`

**Note:** `id`, `body`, `author`, `created_at`, `updated_at`, `system`, `resolvable`

**Discussion:** `id`, `individual_note`, `notes[]`; MR discussions also include `resolved`, `resolved_by`, `resolved_at`, `position` (file path and line for inline review comments)

## Notes vs Discussions

- **Note** — a single root-level comment
- **Discussion** — a thread containing one or more `DiscussionNote` objects
- Use **discussions** when you need MR inline code-review threads, `resolved` status, or `position` (file + line number)
- Use **notes** when you only need a flat list of comments

> `system: true` notes are auto-generated by GitLab (e.g. "assigned to X", "added label Y"). These scripts filter them out with `select(.system == false)`.

## Pagination

GitLab returns 20 items per page by default. Scripts use offset-based pagination with `per_page=100` (the maximum).

| Response header | Meaning |
|-----------------|---------|
| `x-next-page` | Next page number (empty string when on last page) |
| `x-total-pages` | Total number of pages (omitted if result > 10,000) |
| `x-total` | Total item count (omitted if result > 10,000) |
| `Link` | Navigation URLs in RFC 5988 format |

Scripts loop on `x-next-page` and stop when it is empty.

## Error Codes

| Code | Meaning |
|------|---------|
| `401` | Token invalid or expired |
| `403` | Insufficient scope (`read_api` required) or no project access |
| `404` | Project path wrong, iid does not exist, or path not URL-encoded |

## Quick Start (Direct CLI)

```bash
# 1. Set env vars (see Environment Setup above)

# 2. Make scripts executable
chmod +x scripts/fetch-issue.sh scripts/fetch-mr.sh

# 3. Fetch an issue (Markdown output, ready for LLM)
./scripts/fetch-issue.sh mygroup/myproject 42

# 4a. Fetch a merge request (metadata + comments only)
./scripts/fetch-mr.sh mygroup/myproject 101

# 4b. Include the full code diff
./scripts/fetch-mr.sh mygroup/myproject 101 --diff

# 4c. Discussion threads + diff (most complete, best for code review fix)
./scripts/fetch-mr.sh mygroup/myproject 101 --diff --discussions

# 5. Pipe to clipboard and paste into chat
./scripts/fetch-mr.sh mygroup/myproject 101 --diff --discussions | pbcopy
```

### SaaS vs self-hosted

The only difference is `GITLAB_URL`:

```bash
# GitLab.com
export GITLAB_URL=https://gitlab.com/api/v4

# Self-hosted
export GITLAB_URL=https://gitlab.your-company.com/api/v4
```

## Output format

Both scripts output Markdown with stable headings (`#`, `##`, `###`) designed for LLM consumption:

- **Issue output**: `## Metadata` → `## Description` → `## Comments` → `## Related Merge Requests` (best-effort)
- **MR output (default)**: `## Metadata` → `## Description` → `## Comments`
- **MR output (`--diff`)**: adds `## Diff` between Description and Comments
- **MR output (`--discussions`)**: `## Discussions` replaces `## Comments`; threads are grouped with `[resolved]`/`[unresolved]` labels and `Thread on file:line` headings
- **MR output (`--diff --discussions`)**: all sections included

System-generated notes (`assigned to X`, `added label Y`, etc.) are filtered out automatically.

### `MAX_DIFF_LINES_PER_FILE`

When `--diff` is used, diffs are truncated per file to avoid exceeding LLM context limits. Default is **500 lines per file**.

```bash
MAX_DIFF_LINES_PER_FILE=200 ./scripts/fetch-mr.sh mygroup/myproject 101 --diff
```

Set to a larger value for models with larger context windows (e.g. `2000` for Claude).

## Example: feeding to Claude / ChatGPT

**Via Claude Code plugin (recommended):**

```text
/gl:mr mygroup/myproject 101 --diff --discussions
/gl:issue mygroup/myproject 42
```

**Via direct CLI:**

```bash
# MR code review fix: include diff and discussions
./scripts/fetch-mr.sh mygroup/myproject 101 --diff --discussions > mr.md

# Issue implementation: no diff needed
./scripts/fetch-issue.sh mygroup/myproject 42 > issue.md

# macOS: copy directly to clipboard
./scripts/fetch-mr.sh mygroup/myproject 101 --diff --discussions | pbcopy
```

### System prompt — MR review fix

```
You are a senior engineer performing a code review fix.
Below is a merge request with reviewer discussion threads.

For each **unresolved** thread:
1. Quote the file and line (e.g. `src/foo.ts:42`).
2. Restate the reviewer's concern in one sentence.
3. Propose a concrete fix as a unified diff patch.

Skip resolved threads. If a diff is marked as truncated, note which file needs
the full diff and ask for it before proposing a fix for that file.
```

### System prompt — Issue implementation

```
You are a senior engineer implementing a feature or bug fix.
Below is a GitLab issue with its full discussion.

Produce:
(a) A one-paragraph restatement of the problem or requirement.
(b) A ranked implementation plan (steps in logical order).
(c) A list of files likely to be touched, with a one-line rationale for each.
(d) A test strategy (what to test and how).

If the issue is ambiguous, list your assumptions before the plan.
```

### Token budget tips

- Diff is **excluded by default**. Only add `--diff` when you need the LLM to propose code-level fixes.
- Large MRs with many changed files can still exceed context limits even with `--diff`. Lower `MAX_DIFF_LINES_PER_FILE` (e.g. `200`) to cap per-file output.
- Resolved discussions still appear with `[resolved]` labels; instruct the LLM to skip them if only unresolved items are needed.
- The `## Related Merge Requests` section in issue output is best-effort and may be absent if the GitLab instance does not support it.
